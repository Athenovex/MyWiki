# 병합 규칙

새 자료의 지식을 기존 위키와 어떻게 관계 짓고 병합할지에 대한 판단 기준.

## 관계 판정 5가지

새 지식을 발견하면 `10_위키` 검색 후 다음 중 하나로 분류한다.

### SAME — 완전히 동일한 개념
같은 것을 다른 이름·언어·표기로 부를 뿐. → **기존 Canonical Note를 업데이트**. 새 문서를 만들지 않는다.
예: `MCP` / `Model Context Protocol` / `모델 컨텍스트 프로토콜` / `MCP란?`

### BROADER / NARROWER — 상위·하위 개념
포함 관계이지만 각각 독립적으로 설명할 가치가 있는 개념. → **문서 분리 유지 + `related`로 연결**.
예: `API` (상위) ↔ `REST API` (하위)

### RELATED — 관련은 있으나 별도인 개념
같은 맥락에서 자주 언급되지만 서로 다른 대상. → **독립 문서 유지 + 의미 있는 관계만 연결**.
예: `Webhook` / `API` / `HTTP` / `n8n`

### NEW — 기존 위키에 없는 독립 지식
→ **새 Canonical Note 생성**.

## 자동 병합 허용

- 동일 개념의 다른 표기
- 약어 ↔ 정식명칭
- 영어 ↔ 한국어 명칭
- 단순 표기 차이 (대소문자, 띄어쓰기 등)
- 동일 대상임이 명백한 경우

## 자동 병합 금지

- 상위/하위 개념
- 회사/제품
- 기술/구현체
- 방법론/도구
- 조직/서비스
- 강하게 관련되지만 독립된 개념

**확신이 부족하면 병합하지 않는다.** 판단이 애매하면 `80_검토`로 보낸다.

## 기존 Canonical Note 업데이트 절차 (SAME일 때)

1. 기존 내용을 먼저 읽는다.
2. 신규 자료와 중복되는 내용을 확인한다.
3. 신규 정보만 식별한다.
4. 기존의 유효한 설명은 보존한다 (덮어쓰지 않음).
5. 오래된 정보와 충돌하면 근거(날짜·신뢰성)를 비교한다.
6. 충돌하는 정보를 임의로 삭제하지 않는다 — 필요하면 "현재" vs "변경 이력"으로 구분.
7. `sources`에 새 Source Note를 추가하고 `updated` 날짜를 갱신한다.

## 문서가 다른 문서에 흡수될 때

즉시 삭제하지 않는다.

```yaml
---
status: deprecated
merged_into: "[[대표 문서]]"
---
```

로 표시하고 `90_보관`으로 이동한다. 대표 문서의 `aliases`에 병합된 문서의 이름을 추가한다.

## 링크 정책

링크는 의미 있는 지식 관계만 나타낸다. 같은 domain이라는 이유만으로 연결하지 않는다. 링크 개수를 늘리거나 Graph를 예쁘게 만드는 것은 목표가 아니다.
