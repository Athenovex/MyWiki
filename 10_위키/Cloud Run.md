# Cloud Run

> Google Cloud의 완전관리형(서버리스) 컨테이너 플랫폼. 코드만 있으면 인프라 걱정 없이 몇 초 만에 전 세계에 배포할 수 있다.

## Cloud Run이란

[[동국대_교육자료1]] p.20 인포그래픽 "Cloud Run 초고속 배포 — 코드만 있으면 인프라 걱정 없이, 몇 초 만에 전 세계에 안전하게 배포하세요!"의 "1. Cloud Run 이란?" 정의(원문): "Google Cloud의 완전관리형(서버리스) 컨테이너 플랫폼입니다. 인프라 관리 없이 컨테이너 애플리케이션을 자동으로 빌드, 배포, 확장합니다."

## 주요 특징

같은 슬라이드 "1. Cloud Run 이란?" 패널의 4가지 특징(원문):

- **서버리스**: "서버 관리, 패치, 용량 계획 불필요"
- **자동 확장**: "트래픽에 따라 자동으로 확장/축소 (0 → N)"
- **빠른 배포**: "컨테이너 이미지 푸시 후 몇 초 만에 배포 완료"
- **전 세계 제공**: "전 세계 엣지에서 빠르고 안전하게 서비스 제공"

## 배포 흐름

같은 슬라이드 "2. Cloud Run 배포 흐름" 패널의 5단계(원문): 코드 개발(로컬에서 코드 작성) → 컨테이너 이미지 빌드(Dockerfile로 이미지 생성) → 이미지 저장(Artifact Registry에 저장) → Cloud Run 배포(이미지 선택 후 배포 클릭) → 자동 확장 & 서빙(트래픽에 따라 자동 확장, 안정적으로 서비스 제공).

같은 패널 하단에는 실제 요청 처리 경로도 그려져 있다: 사용자 요청 → Cloud Load Balancing → Cloud Run 서비스(요청에 따라 인스턴스 자동 생성/축소되는 컨테이너 여러 개) → 데이터베이스 및 외부 서비스.

### 배포 명령어 — 슬라이드에 실린 실제 예시

아래는 편집자가 지어낸 예시가 아니라, p.20 슬라이드 "4. 배포 방법 (예시)" 패널에 그대로 실려 있는 명령어를 그대로 옮긴 것이다.

```bash
# 1. 이미지 빌드
docker build -t gcr.io/PROJECT_ID/my-app .
# 2. 이미지 푸시
docker push gcr.io/PROJECT_ID/my-app
# 3. Cloud Run 배포
gcloud run deploy my-app \
  --image gcr.io/PROJECT_ID/my-app \
  --region asia-northeast3 \
  --platform managed \
  --allow-unauthenticated
```

> 참고(일반 배경지식, 출처에 없음): `--region`은 서비스를 배포할 물리적 위치(예: 서울 인근 asia-northeast3)를 지정하고, `--platform managed`는 자체 GKE 클러스터 없이 Google이 완전히 관리하는 환경에서 실행하겠다는 뜻이며, `--allow-unauthenticated`는 별도 인증 없이 누구나 접근 가능한 공개 엔드포인트로 열겠다는 옵션이다. 내부 전용 서비스라면 이 옵션을 빼고 IAM으로 접근을 제한한다. (명령어 자체는 슬라이드 원문이지만, 이 옵션들에 대한 해설은 슬라이드에 없어 편집 과정에서 보충했다.)

슬라이드에는 Dockerfile 본문 자체는 실려 있지 않다. 아래는 [[Streamlit]] 앱을 컨테이너화하는 최소 Dockerfile 예시로, 편집 과정에서 작성했다(원본 자료의 실제 코드는 아님).

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["streamlit", "run", "app.py", "--server.port=8080", "--server.address=0.0.0.0"]
```

## 장점

같은 슬라이드 "3. 초고속 배포의 장점" 5가지(원문): "몇 초 만에 배포 완료 — 이미지 업로드 후 클릭 한 번으로 서비스 즉시 실행", "트래픽 급증에도 자동 대응 — 자동 확장으로 성능 저하 없이 안정적 운영", "비용 절감 — 요청이 없으면 0으로 축소되어 사용한 만큼만 비용 지불", "운영 부담 최소화 — 서버, 인프라, OS 관리 없이 개발에만 집중 가능", "전 세계 빠른 응답 — Google 글로벌 네트워크를 통한 낮은 지연시간 및 높은 가용성".

## 주요 기능

같은 슬라이드 "5. 주요 기능" 6가지(원문): 동시 요청 처리("높은 동시성능 지원하는 확장성"), 리비전 관리("트래픽 분할 및 롤백이 쉬운 배포"), 환경변수/비밀 관리("Secret Manager와 연동"), VPC 연결("안전한 내부 네트워크 액세스 지원"), Cloud Monitoring("로깅, 모니터링, 알림 제공"), IAM 통합("세밀한 권한 제어로 안전한 운영").

## 활용 사례

같은 슬라이드 "6. 사용 사례" 5가지(원문): 웹 애플리케이션 & API, 모바일 백엔드 서비스, AI/ML 모델 서빙, 이벤트 기반 처리 작업, 마이크로서비스 아키텍처.

슬라이드 한 줄 요약(원문): "Cloud Run은 서버 관리 없이 컨테이너를 몇 초 만에 배포하고, 트래픽에 맞춰 자동 확장하여 안정적으로 서비스를 운영할 수 있게 해주는 초고속 서버리스 플랫폼입니다."

## 비교: Cloud Run vs 전통적 VM(가상 머신) 호스팅 (참고)

> 출처 자료에 없는 일반적 비교로, 이해를 돕기 위해 편집 과정에서 추가했다.

| 항목 | Cloud Run(서버리스 컨테이너) | Compute Engine 등 전통적 VM |
|---|---|---|
| 인프라 관리 | Google이 대신 처리 | 직접 OS 패치·용량 계획 필요 |
| 확장 | 요청량에 따라 자동으로 0~N | 수동 또는 별도 오토스케일링 그룹 설정 필요 |
| 유휴 비용 | 요청 없으면 0으로 축소, 비용 없음 | 켜져 있는 동안 계속 과금 |
| 실행 시간 제약 | 요청-응답 기반 워크로드에 적합, 장시간 상시 실행 프로세스에는 제약이 있을 수 있음 | 상시 실행 프로세스·특수 런타임 요구에 자유로움 |
| 적합한 사례 | API 서버, 웹앱, 이벤트 처리 | 상시 백그라운드 작업, 특수 소프트웨어 스택 |

트래픽이 들쭉날쭉하거나 운영 인력이 적은 팀에는 Cloud Run처럼 자동으로 늘고 줄어드는 서버리스 방식이 유리하고, 상시 켜져 있어야 하는 프로세스나 세밀한 OS 제어가 필요한 경우는 VM 기반 호스팅이 더 적합할 수 있다.
