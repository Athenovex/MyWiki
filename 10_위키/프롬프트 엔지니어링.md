# 프롬프트 엔지니어링

> LLM에게 원하는 답변을 얻기 위해 질문(프롬프트)의 내용·구조·맥락을 설계하는 기법. 명확성·구체성·맥락 제공이 핵심이다.

## 개요

GPT 같은 LLM은 "거대한 도서관"과 같아서, 일반적인 질문에는 일반적인 답변만 한다. 특정 전문 지식을 꺼내 쓰려면 질문(프롬프트)으로 모델이 원하는 맥락에 집중(attention)하도록 유도해야 한다.

## 기본 원칙

- **명확성**: "날씨가 어때?"(X) → "서울의 현재 날씨가 어때?"(O)
- **상세성**: 구체적인 요구사항을 명시
- **문맥 이해**: 이전 대화 맥락을 참조하도록 지시
- **맥락 정보 제공**: 질문의 배경·목적·대상 독자를 포함
- **단계별 세분화**: 복잡한 요청을 단계별로 나누고 예시 제시

## 프롬프트 구성 요소

여러 출처에서 공통적으로 등장하는 구성 요소 체계:

| 요소 | 설명 |
|---|---|
| 역할/페르소나 (Role/Persona) | AI에게 수행할 역할·전문성 부여 ("당신은 10년 경력 데이터 분석가입니다") |
| 목표/명령 (Task) | 무엇을 원하는지 명확히 지시 |
| 맥락 (Context) | 배경·대상·제약조건 |
| 예시 (Example) | 원하는 형식·품질의 예시 제공 |
| 형식/출력 (Format) | 출력 구조·비율·길이 지정 |
| 톤/어조 (Tone) | 말투·문체 지정 |

역할을 구체적으로 쓸수록 좋다 ("전문가야" X → "10년 경력의 데이터 사이언티스트야" O).

## 11개 프롬프트 엔지니어링 기법

OpenAI·Google·Stanford·Princeton·DeepMind 등이 논문으로 제안한 기법들 ([[프롬프트엔지니어링]] p.7-51). 아래 예시 프롬프트는 이해를 돕기 위해 위키 편집 과정에서 작성한 것으로, 원본 PDF에 실린 예시 문구와 동일하지 않을 수 있다 (개념·정의는 출처 기반, 예시 문구는 편집자 작성).

### 1. 제로샷 (Zero-Shot)

예시 없이 지시문만으로 답변을 유도. 모델의 사전학습 지식에 전적으로 의존한다.

```
다음 문장의 감정을 긍정/부정/중립 중 하나로만 답해줘.
문장: "오늘 날씨가 정말 좋다"
```

빠르고 프롬프트가 짧지만, 원하는 출력 형식이 특이하거나 작업이 복잡할수록 정확도가 떨어진다.

### 2. 원샷 (One-Shot)

예시를 정확히 1개 제시한 뒤 유사한 작업을 요청. "이런 형식으로 답하라"는 기준점을 하나 제공한다.

```
입력: "배송이 너무 느려요" → 감정: 부정
입력: "제품이 마음에 들어요" → 감정:
```

제로샷보다 출력 형식이 안정적으로 통일된다.

### 3. 퓨샷 (Few-Shot)

예시를 2~5개 제공해 다양한 패턴(긍정/부정/중립, 짧은 예/긴 예 등)을 보여주고 모델이 규칙을 일반화하도록 유도한다.

```
입력: "배송이 너무 느려요" → 감정: 부정
입력: "그냥 그래요, 특별하진 않아요" → 감정: 중립
입력: "재구매 의사 100%입니다" → 감정: 긍정
입력: "포장이 파손된 채 왔어요" → 감정:
```

예시가 늘수록 일관성은 좋아지지만 토큰 비용도 늘어나므로 2~5개 사이에서 균형을 잡는다. 분류·형식 변환·문체 모사 작업에 특히 효과적.

### 4. 역할 부여 프롬프트 (Role/Persona Prompting)

"너는 이제 ~야"로 AI에게 구체적 역할·전문성·경험을 지정하면 답변의 어휘 수준·관점·정보 깊이가 그 역할에 맞게 바뀐다.

```
너는 10년 경력의 세무사야. 1인 사업자가 처음 종합소득세를
신고할 때 놓치기 쉬운 부분 위주로 절차를 설명해줘.
```

"전문가야"(X)보다 "10년 경력의 데이터 사이언티스트야"(O)처럼 역할을 구체적으로 쓸수록 효과가 크다.

### 5. Chain of Thought (CoT, 사고의 연쇄)

복잡한 문제를 한 번에 답하게 하지 않고 "단계별로 생각해봐"처럼 중간 추론 과정을 거치도록 유도. 수학·논리 문제에서 정확도가 크게 향상된다.

```
철수는 사과를 5개 갖고 있었다. 마트에서 3개를 더 샀고,
그중 2개를 간식으로 먹었다. 단계별로 계산해서
철수에게 남은 사과 개수를 알려줘.
```

모델이 중간 계산·근거를 노출하므로 사람이 오류를 검증하기도 쉬워진다.

### 6. Tree-of-Thought (ToT, 사고의 나무)

CoT를 확장한 개념. 하나의 추론 경로만 따라가지 않고 여러 해결 방법을 나뭇가지처럼 동시에 분기 탐색한 뒤, 각 분기를 평가해 최선의 경로를 선택한다.

```
신제품 텀블러의 마케팅 문구를 3가지 다른 컨셉
(① 가격 강조 ② 친환경 강조 ③ 디자인 강조)으로
각각 3줄씩 작성한 다음, 20대 타겟 기준으로
가장 설득력 있는 컨셉 1개를 근거와 함께 골라줘.
```

CoT보다 토큰 소모가 크지만, 정답이 하나가 아닌 창의적 문제·전략 수립에서 더 견고한 답을 낸다.

### 7. ReAct (Reasoning + Acting)

추론(Reasoning)과 행동(Acting)을 번갈아 수행하는 루프. **Thought(생각) → Action(도구 호출/검색 등) → Observation(결과 관찰)** 을 반복하며 답을 완성해간다.

```
Thought: 이 질문에 답하려면 오늘 환율 정보가 필요하다.
Action: search("오늘 원/달러 환율")
Observation: (검색 결과가 여기 채워짐)
Thought: 이제 100달러를 원화로 환산할 수 있다.
Action: 최종 답변 작성
```

단순 텍스트 생성이 아니라 검색·계산기 등 외부 도구와 결합된 에이전트형 작업에 적합.

### 8. 제어 지시 프롬프트 (Instruction Prompting)

"무엇을, 어떻게 하라"를 모호함 없이 명령형으로 명시. 대상(무엇을)·조건(어떻게)·제약(길이/형식)을 동시에 담는 것이 핵심.

```
아래 이메일 본문을 3문장 이내로 요약해줘.
마지막 줄에는 "다음 행동:"으로 시작하는
액션 아이템을 굵게 표시해줘.
```

### 9. 자기 피드백 / 자기 정제 (Self-Refinement)

모델이 자신의 초안 응답을 스스로 비평하고 수정하도록 한 번 더 요청하는 2단계 기법.

```
1단계: "위 질문에 답해줘." (초안 생성)
2단계: "방금 네가 작성한 답변을 검토해서
논리적 허점이나 근거 부족한 부분을 찾아 지적한 뒤,
그 지적을 반영해서 다시 작성해줘."
```

[[프롬프트 엔지니어링#LLM 답변 교차 검증 (API 없이)|LLM 답변 교차 검증]]의 "생성 → 비판적 검토 → 사실 검증 → 최종 수정" 흐름이 이 기법의 실무 확장판. 환각(할루시네이션) 감소, 논리적 허점 보완에 효과적.

### 10. 출력 제어 (Output Control)

답변의 형식·구조·스타일을 프롬프트 단에서 명확히 지정. 후처리(파싱, 자동화 연동)가 필요할 때 특히 중요하다.

```
결과를 JSON으로만 반환해줘. 다른 설명 문장은 붙이지 마.
{
  "title": "...",
  "summary": "..." (2문장 이내)
}
```

### 11. 질의 최적화 (Query Optimization)

프롬프트(질문) 자체의 표현·어순·구조를 개선해 모델이 의도를 더 정확히 파악하도록 다듬는 메타 기법. 다른 10개 기법을 적용하기 전, 질문 문장 자체를 명확하게 재작성하는 작업이다.

```
Before: "날씨 어때?"
After:  "서울의 오늘 오후 날씨와 강수 확률을 알려줘.
         우산이 필요한지도 판단해줘."
```

[[프롬프트 엔지니어링#언어·협업 관점|언어·협업 관점]] 메모: 영어 프롬프트가 토큰당 정보 밀도가 높아 더 전문적인 답변을 얻는 경향이 있다는 점도 이 최적화의 연장선.

## 실무 프롬프트 엔지니어링 (환각 방지 포함)

[[동국대_교육자료1]] p.7의 실무 프레임워크:

- **AI 페르소나 설계**: 역할·경험·전문분야·목표·제약조건
- **Tone & Manner 부여**: 말투(친절/전문가다운/공식적/간결/유머러스)와 답변 스타일(단계별/표/예시포함/코드포함/요약)
- **환각(Hallucination) 방지 7가지 기법**: ①모르면 모른다고 답하기 ②근거 제시 ③추론과 사실 구분 ④출처 표시 ⑤불확실성 표현 ⑥범위 제한(문서 안에서만 답변) ⑦단계별 검증

프롬프트 품질은 역할(Persona)·표현 방식(Tone&Manner)·제약조건(환각 방지)·출력 형식을 얼마나 구체적으로 설계했는지에 좌우된다.

## LLM 답변 교차 검증 (API 없이)

[[동국대_교육자료1]] p.8: 여러 LLM(ChatGPT/Claude/Gemini) 또는 하나의 LLM에 프롬프트를 활용해 답변의 정확성을 높이는 방법. 동일 질문 여러 LLM 입력, 반대 의견 요청, 교수+리뷰어 역할 채점, 사실 검증 전용 프롬프트, 출처 강제, AI 배심원 방식, 검증 전문가 프롬프트 등 8가지 패턴. 추천 흐름: 생성 → 비판적 검토 → 사실 검증 → 최종 수정.

## 3단 프롬프트 구조 (실무 간소화 버전)

[[AI미디어콘텐츠_크리에이터과정_교안]] p.9: `#역할부여 → #지시사항 → #반영사항(세부 조건 나열)` 3단 구조로 실무에서 빠르게 활용.

## 언어·협업 관점

- 영어 프롬프트가 토큰이 적어 더 길고 전문적인 답변을 얻는 경향. 영어권 자료가 많은 분야는 영어로, 한국 특화 자료가 필요하면 한국어로 질문.
- 상호 협력 관점: 한 번에 완성하지 않고 단계적으로 대화하며 답변을 개선.
- 업무 도메인 지식(메타 인지)이 충분할수록 좋은 프롬프트가 나온다.

## 목표-대상-컨텍스트 프롬프트 공식 (실무 7요소)

[[새 프롬프트 공식]]이 제시하는 실무형 프롬프트 골격. 위 11개 기법이 "생성 방식"을 다룬다면, 이 공식은 "요청 자체를 빠짐없이 구조화"하는 데 초점을 둔다.

| 요소 | 작성 내용 |
|---|---|
| 목표 | 이 결과물을 통해 사용자가 어떤 행동을 하게 만들고 싶은지 |
| 대상 | 누가 읽거나 사용할 것인지 |
| 컨텍스트 | 현재 상황, 배경, 자료, 제약 조건 |
| 평가 기준 | 좋은 결과물의 기준 |
| 작업 순서 | 먼저 무엇을 판단하고, 그다음 무엇을 만들지 |
| 출력 형식 | 표, 단계별, 문구안, 보고서, 체크리스트 등 |
| 검토 요청 | 초안 작성 후 약점을 찾고 개선안까지 제시하도록 지시 |

작업 방식은 "기준 정리 → 초안 작성 → 개선본 제시" 3단계로 흐르도록 지시하는 것이 핵심이며, 결과물도 이 순서(기준 정리/초안/문제점/개선본/최종본)로 받으면 품질을 눈으로 점검하기 쉽다.

## 나쁜 프롬프트 → 좋은 프롬프트 (표현 치환)

[[올바른 프롬프트 100선]]이 제시하는 "즉석에서 바꿔 쓰는" 표현 치환 원칙. 막연한 요청을 구체적 기준으로 바꾸면 결과물 품질이 즉시 달라진다는 것이 핵심 주장이다.

| 막연한 요청 | 구체화된 요청 |
|---|---|
| "요약해줘" | "서론 빼고 3줄로 요약해줘" |
| "개선해줘" | "이 3가지 요소를 개선시켜줘: 진실성, 글의 흐름, CTA" |
| "더 전문적으로 써줘" | "고객이 5초 안에 이해할 수 있게 명확하게 써줘" |
| "설명해줘" | "수치와 구체적인 사례를 통해 설명해줘" |
| "이게 뭐야?" | "뻔하지 않은 관점으로 알려줘" |
| "~팁 알려줘" | "이 생각에 반박해봐" |

원칙은 두 가지로 요약된다: **① 모호한 동사(요약/개선/설명)에는 반드시 기준이나 형식을 덧붙인다. ② "전문적으로", "더 좋게"처럼 추상적인 형용사 대신 측정 가능한 조건(글자 수, 관점, 반박 여부)으로 바꾼다.**

## 단축 명령어 (프롬프트 코드) 모음

프롬프트 앞이나 뒤에 짧은 코드를 붙이는 것만으로 AI의 응답 방식을 지정하는 기법. ChatGPT·Claude·Gemini 등 도구에 무관하게 작동하며, [[AI 프롬프트 단축어 100선]]·[[복붙해서 바로 쓰는 AI 프롬프트 명령어 40]]·[[클로드 비밀코드 100개]] 세 출처에서 공통적으로 100개 이상의 코드가 소개된다. 아래는 카테고리별 대표 사례다 (전체 목록은 각 출처 문서 참고).

## 프롬프트 조합(콤보) 기법

[[클로드 비밀코드 100개]]가 제시하는, 여러 단축 코드·기법을 한 프롬프트에 겹쳐 쓰는 응용법. 단일 기법보다 위력이 커진다.

- **역할 + 태그 + 예시 콤보**: "너는 카피라이터야" + `<맥락></맥락> <지시></지시>` 형태의 XML 태그 구조 + 예시 2개를 함께 제공
- **플랜 → 실행 콤보**: 계획을 먼저 승인받은 뒤 실행 (Claude Code의 `/plan`이 대표적 구현)
- **초안 → 비평 → 수정 콤보**: "초안 써줘" → "냉정하게 비평해줘" → "비평 반영해서 다시" 3턴이면 품질이 확연히 달라짐
- **페르소나 인터뷰 콤보**: "너는 내 타깃 고객이야. 이 상품에 대해 솔직하게 말해줘" — 시장조사를 대화 한 번으로 대체
- **목차 → 섹션별 콤보**: 목차를 먼저 승인받은 뒤 섹션 하나씩 채워 긴 글의 방향이 틀어지는 것을 방지

## 생성 파라미터로 AI 티 줄이기 (temperature 등)

[[AI글 사람이 쓴 글로 바꾸는 4단계]]가 제시하는, 프롬프트 텍스트가 아니라 **모델 API 파라미터**로 문체의 "감정 온도"를 조절하는 방법. Claude·ChatGPT API나 일부 플레이그라운드에서 직접 값을 지정할 수 있다.

| 파라미터 | 역할 | 값이 높을수록 |
|---|---|---|
| `temperature` | 문장의 창의성·감정선 결정 (샘플링 확률 조절) | 다양하고 예측 불가능한 문장 (감정적·창의적 글에 유리, 1.3 이상은 비논리적으로 흐를 위험) |
| `top_p` | 선택 가능한 단어의 확률 상위 집합 제한 | 더 다양한 어휘, 자연스러운 표현 확장 |
| `frequency_penalty` | 동일 단어 반복 억제 | 반복이 줄고 문장 리듬감이 좋아짐 (너무 높으면 핵심 키워드까지 억제될 수 있음) |
| `presence_penalty` | 이미 언급한 주제에서 벗어나 새 아이디어 시도 유도 | 새로운 관점 시도 (너무 높으면 맥락과 무관한 단어 등장 위험) |

용도별 추천 조합: 공식 문서/리포트(temperature 0.8·top_p 0.7·frequency_penalty 0.5·presence_penalty 0.3), 블로그/감성글(1.0~1.1·0.9·0.7·0.5), 창작/에세이/카피라이팅(1.1~1.2·0.95·0.7·0.6). 이 값들은 API·플레이그라운드 환경에서 유효하며, 일반 챗봇 UI에서는 프롬프트 텍스트로 "감정이 느껴지는 자연스러운 문체로, 조금 덜 완벽하고 인간적인 결이 느껴지게" 요청하는 방식으로 유사한 효과를 노릴 수 있다(원문에서 도출된 응용).
